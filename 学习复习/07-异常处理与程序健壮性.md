## 二、两个核心问题

### 问题 1：`try/except` 只管「程序崩不崩」，不管「数据对不对」

`jump("-10")` **完全合法地通过**了——因为 `int("-10")` 成功返回 `-10`，一点错都不出。于是猫跳了负十厘米。

> 🔑 **异常处理是「兜住崩溃」，业务校验是「拦住荒谬」。两件事必须分开做。**

`int()` 的真实边界，我实测了一遍：

```text
int("50")        -> 50          正常
int("  50  ")    -> 50          首尾空格无所谓，能转
int("50.0")      -> ValueError: invalid literal for int() with base 10: '50.0'
int("1.5")       -> ValueError: invalid literal for int() with base 10: '1.5'
int("很多")       -> ValueError: invalid literal for int() with base 10: '很多'
```

注意第 3、4 行：**`int()` 不接受小数字符串**，`"50.0"` 也照样 `ValueError`。要转小数得 `int(float("50.0"))`（实测得 `50`，直接截断）。这说明「用 `try/int` 代替 `isdigit()`」这条改进路线是对的（见 [01-基础语法与流程控制.md](file:///E:/python%E6%BA%90%E7%A0%81/python%E5%B7%A5%E4%BD%9C%E5%8C%BA/lreaning/%E5%AD%A6%E4%B9%A0%E5%A4%8D%E4%B9%A0/01-%E5%9F%BA%E7%A1%80%E8%AF%AD%E6%B3%95%E4%B8%8E%E6%B5%81%E7%A8%8B%E6%8E%A7%E5%88%B6.md) 里 `loop-01.py` 的负数 bug），但转成功之后**还得自己判范围**。

### 问题 2：`except ZeroDivisionError` 是**永远不会执行**的死代码

`jump` 里没有除法、没有 `%`，所以这个分支没有任何触发路径。那句提示「分母不能为 0」也说明它是从别处复制来的。

危害不是「多四行」，而是：**读代码的人会以为这里可能出除零错误**，进而对整段逻辑产生错误预期。

> 📌 立一条规矩：**只捕获你能现场复现的异常。** 想证明 `except X` 该存在，就写一行代码让它真的抛 `X` 给你看。写不出这一行，就删掉这个分支。

## 三、修正版：用 `raise` 把校验和兜底接起来

推荐的做法是**在业务不合法时主动抛同一个异常**，让下面唯一的 `except` 一次处理完。这样校验和兜底走同一条路径，不会出现「一条漏网」。

```python
class SmartCat:
    def __init__(self, name):
        self.name = name

    def jump(self, height):
        try:
            h = int(height)
            if h <= 0:                                  # 业务校验：主动抛
                raise ValueError(f"高度必须是正数，{h} 厘米跳不起来")
            print(f"{self.name}跳了{h}厘米高！")
        except ValueError as e:                          # 一个分支管住两种错
            print(f"❌ 错误：{e}")
        finally:
            print(f"{self.name}的一次跳跃尝试结束了。\n")
```

实际输出：

```text
tom跳了50厘米高！
tom的一次跳跃尝试结束了。

❌ 错误：invalid literal for int() with base 10: '很多'
tom的一次跳跃尝试结束了。

❌ 错误：高度必须是正数，-10 厘米跳不起来
tom的一次跳跃尝试结束了。
```

三种输入都走同一条出口，`finally` 一次不落。负数这次被真正拦下了。

> 💡 副作用：`int("很多")` 那条现在打印的是 Python 的**英文原始信息**，对用户不友好。两种解法，按场景选。

**解法 A：分两个 `except`，各给各的文案**

```python
class SmartCat:
    def __init__(self, name):
        self.name = name

    def jump(self, height):
        try:
            h = int(height)
            if h <= 0:
                raise ValueError(f"高度必须是正数，{h} 厘米跳不起来")
            print(f"{self.name}跳了{h}厘米高！")
        except TypeError:
            print("内部错误：参数类型不对")            # 程序 bug，不给用户看
        except ValueError as e:
            print(f"听不懂 '{height}'，请输入数字")     # 用户错误，给友好文案
        finally:
            print(f"{self.name}的一次跳跃尝试结束了。\n")
```

**解法 B（更省事）：文案里带上原始输入，别带 Python 的话**

```python
        except ValueError:
            print(f"❌ 错误：'{height}' 不是有效的正整数高度")
```

原则：**给用户看的话自己写，给程序员看的话让 Python 写**（用 `as e` 拿到原始异常，需要时打印或记日志）。

### 还差一步：调用方怎么知道成功没成功？

现在 `jump` 出错时返回 `None`，成功时也返回 `None`——**外面完全看不出来**。这在你的通讯录里已经是既成习惯了（[contacts.py:45-55](file:///E:/python%E6%BA%90%E7%A0%81/python%E5%B7%A5%E4%BD%9C%E5%8C%BA/lreaning/contacts.py#L45) 返回 `(ok, message)`），类方法同样适用：

## 四、完整的四段结构（含实测语义）

```python
def jump(height):
    try:
        h = int(height)                      # 可能崩的代码放这里，且只放这里
    except ValueError as e:                  # 出了上面那行预期的错
        print("参数错误", e)
    else:                                    # ← 只有 try 完全成功才执行
        print(f"跳了 {h} 厘米")
    finally:                                 # ← 无论如何都执行
        print("尝试结束")
```

实测（分别喂 `"50"`、`"-10"`、`"很多"`）：

```text
跳了50厘米
尝试结束
参数错误：高度必须是正数
尝试结束
参数错误：invalid literal for int() with base 10: '很多'
尝试结束
```

各段职责：

| 段 | 何时执行 | 该放什么 | 不该放什么 |
| --- | --- | --- | --- |
| `try` | 顺序执行，一崩就跳走 | **只放那一两行会崩的** | 一大坨逻辑（会搞不清哪行出的错） |
| `except E as e` | 抛了 `E` 且类型匹配 | 恢复动作 + 用户提示 | 静悄悄 `pass`（等于把错误扔掉） |
| `else` | `try` **没抛异常**才执行 | 成功后的正式逻辑 | 又可能崩的操作（它不在保护范围内！） |
| `finally` | **一定执行**，包括 `return` 之后 | 关文件、关连接、收尾日志 | `return`（见下） |

`else` 的价值：**把「保护范围」和「成功之后要做的事」分开**。如果写在大 `try` 里，`else` 段自己出的 bug 会被你误当成输入错误处理掉。

### 关于 `finally` 的两个实测真相

**① `finally` 在 `return` 之后、函数真正结束之前执行：**

```text
   try 里
   finally 里（在 return 之后、函数真正结束之前）
   -> 返回值
```

**② 在 `finally` 里写 `return` 会吞掉异常**——Python 自己都会警告：

```text
SyntaxWarning: 'return' in a 'finally' block
g() -> 我在 finally 里 return 了     ← 原本的 ValueError 完全看不见了
```

所以：**`finally` 里绝不 `return`，也绝不抛新异常**，否则真实错误会被抹掉。

### ③ 裸 `except:` 和 `except Exception` 的区别（实测）

```text
except Exception:     没接住 KeyboardInterrupt，Ctrl+C 仍能退出程序
except BaseException: 捕获到了 KeyboardInterrupt
```

这条决定了一个硬规则：**永远不要写 `except:`（裸的）**，因为它等价于 `except BaseException`，会把用户按 Ctrl+C 的退出意图、`SystemExit`、内存告警一起吞掉，程序变成杀不死的僵尸。要兜底就写 `except Exception`——它是**所有普通程序错误**的基类，但不含 `KeyboardInterrupt` / `SystemExit`。

## 五、异常层级与 `except` 的顺序（实测）

```text
BaseException
 ├── SystemExit                （sys.exit()）
 ├── KeyboardInterrupt          （Ctrl+C）
 └── Exception                  ← 你该捕获的这一层
      ├── ValueError            （类型对但值不对：int("很多")）
      ├── TypeError             （参数类型不对）
      ├── LookupError
      │    ├── KeyError          （字典没这个键）
      │    └── IndexError        （列表下标越界）
      ├── OSError                （文件/网络，含 FileNotFoundError）
      ├── ZeroDivisionError
      └── AttributeError         （对象没这个属性/方法）
```

`except` 是**从上往下第一个匹配就执行**，所以顺序必须「先具体、后笼统」。实测的反例：

```text
   被 Exception 抢先捕获: ValueError     ← 下面再写 except ValueError 就是死代码
```

```python
try:
    int(x)
except Exception as e:        # ❌ 太早，抢走了所有细节
    ...
except ValueError as e:       # 永远进不来
    ...
```

**你以后最常遇到的四个，认名字要熟：**

| 异常 | 什么时候抛 | 你的代码里出现过 |
| --- | --- | --- |
| `ValueError` | 类型对、值不对（`int("很多")`、`raise ValueError`） | `18_try_except.py` |
| `KeyError` | `dict["没这个键"]` | 学习总结里记过（`= 打成 -` 那次） |
| `AttributeError` | `obj.没这个属性/方法` | `13_spider.py:22`、`Cat.age` |
| `TypeError` | 类型不对（`"a" + 1`）、参数个数不对 | 方法忘写 `self` 时 |
| `IndexError` | 列表下标越界 | `14_spider_save.py` 配对不等长时会抛 |
| `FileNotFoundError` | `open()` 找不到文件（是 `OSError` 的子类） | 你用 `os.path.exists` 提前避开了 |

**读 traceback 的正确姿势**：从**最后一行**往上读。最后一行是「什么错 + 为什么」，往上是「谁调了谁」，**最靠近底部的 `File ... line N` 才是你的代码出的错**，越往上越是框架内部。你 06/07 里那些守卫式 `if` 其实就是在避免走到这些异常。

## 六、回头看你写对的地方：`load_data` 的三层防御

[07_file_test.py:6-18](file:///E:/python%E6%BA%90%E7%A0%81/python%E5%B7%A5%E4%BD%9C%E5%8C%BA/lreaning/07_file_test.py#L6)（v4 里是 [contacts.py:14-30](file:///E:/python%E6%BA%90%E7%A0%81/python%E5%B7%A5%E4%BD%9C%E5%8C%BA/lreaning/contacts.py#L14)）：

```python
if not os.path.exists(FILE_NAME):        # ① 不用 try 兜：能预判就别抛异常
    return {}
try:
    with open(FILE_NAME, "r", encoding="utf-8") as f:
        data = json.load(f)
except (json.JSONDecodeError, OSError):  # ② 一次捕获多个类型，写在元组里
    print("通讯录文件损坏或无法读取，已按空通讯录启动。")
    return {}
if not isinstance(data, dict):           # ③ 捕获成功 ≠ 数据正确
    print("通讯录文件格式不正确，已按空通讯录启动。")
    return {}
```

三层各有分工，这正是健壮程序的样子。两个可提炼的写法：

- **`except (A, B):`** 用元组一次捕获多类。这里 `JSONDecodeError` 管「文件坏了」，`OSError` 管「没权限 / 被别的程序占用 / 磁盘问题」。
- **能预判的先用 `if` 预判**（`os.path.exists`），**预判不了的才用 `try`**。因为「文件不存在」是常态，不该靠异常来控制流程；而「文件内容坏了」无法预判，只能 `try`。

## 七、`assert` 不能当异常处理（和 01 号文档呼应）

[check_age.py:4-5](file:///E:/python%E6%BA%90%E7%A0%81/python%E5%B7%A5%E4%BD%9C%E5%8C%BA/lreaning/check_age.py#L4) 用的 `assert` 属于「自我检查」，不是异常处理，**别混用**：

```python
assert 0 <= score <= 100      # 开发期自查：违反说明代码有 bug
if not 0 <= score <= 100:     # 正式校验：违反的是用户输入，必须给友好提示
    raise ValueError("成绩必须在 0~100 之间")
```

差别在于 `python -O 文件.py` 会**把所有 `assert` 直接优化掉**（不执行）。业务校验被偷偷删掉是严重事故，所以校验一律用 `if + raise`。
