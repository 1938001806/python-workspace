## 一、18_try_except.py 逐行读

```python
class SmartCat:
    def __init__(self, name):
        self.name = name

    def jump(self, height):
        try:
            h = int(height)                       # :6
            print(f"{self.name}跳了{h}厘米高！")    # :7
        except ValueError:                        # :9
            print(f"❌ 错误：{self.name}听不懂'{height}'是什么高度，请输入数字！")
        except ZeroDivisionError:                 # :12
            print("❌ 错误：分母不能为0！")
        finally:                                  # :14
            print(f"{self.name}的一次跳跃尝试结束了。\n")

my_cat = SmartCat("tom")   # :17
my_cat.jump("50")          # :18
my_cat.jump("很多")         # :19
my_cat.jump("-10")         # :20
```

实际输出：

```text
tom跳了50厘米高！
tom的一次跳跃尝试结束了。

❌ 错误：tom听不懂'很多'是什么高度，请输入数字！
tom的一次跳跃尝试结束了。

tom跳了-10厘米高！
tom的一次跳跃尝试结束了。
```

三段输出，三段 `finally`。结构本身写得对：正常路径、异常路径都走到了收尾。问题在「什么算异常」这个判断上。

## 二、第一个问题：`-10` 不是异常，但它不是有效数据

`int("-10")` 完全合法，所以 `:6` 不抛异常，`:7` 照常打印「跳了-10厘米高」。程序没崩，数据是荒谬的。

实测 `int()` 的接受面：

```text
'50'    -> 50
' 50 '  -> 50        # 前后空格自动忽略
'+50'   -> 50
'50.0'  -> ValueError
'1e2'   -> ValueError
'五十'  -> ValueError
''      -> ValueError
```

`try/except` 只回答「这行代码能不能执行完」，不回答「执行完的结果对不对」。**业务规则必须自己写**，而且应该用 `raise` 主动制造异常，让调用方没机会忽略：

```python
def jump(height):
    h = int(height)
    if h <= 0:
        raise ValueError(f"高度必须是正数，收到 {h}")
    return h
```

实测：

```text
'50'   -> 50
'0'    -> ValueError: 高度必须是正数，收到 0
'-10'  -> ValueError: 高度必须是正数，收到 -10
'很多' -> ValueError: invalid literal for int() with base 10: '很多'
```

注意 `0` 也被挡掉了。如果业务上允许 0（原地跳），把条件改成 `h < 0` 即可——**边界值要显式决定，不能靠默认**。

## 三、第二个问题：`except ZeroDivisionError` 是死代码

`jump` 的 `try` 里只有 `int()` 和 `print()`，**没有任何除法**。用 AST 数一下 [18_try_except.py](../18_try_except.py) 里 `jump` 的除法节点：

```text
jump() 里除法节点的数量: 0
```

所以 `:12-13` 永远不会执行。它不报错、不影响输出，只是让你误以为「除零已经处理了」。

修法只有两个：要么删掉这个分支，要么在 `try` 里真的有除法。**不能执行的 `except` 比没有更糟**，因为它会骗过代码审查。

---

## 四、第三个问题：`TypeError` 不在捕获范围

`:9` 只捕获 `ValueError`。如果传进来的是 `None`：

```text
my_cat.jump(None)
-> finally 先执行
-> TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
```

两个信息值得记住：

1. `int(None)` 抛的是 `TypeError`，不是 `ValueError`。**异常类型要按实际会发生的来写**，不是按「输入不对」这个笼统概念来写。
2. `finally` 在异常继续向上传播**之前**执行。所以即使没人接住，收尾代码仍然跑了一次：

```text
finally 执行
上层收到: TypeError
```

如果希望 `jump` 对任何非法输入都给出友好提示，可以捕获 `(ValueError, TypeError)`；但更推荐的做法是**先校验类型**，把「不是字符串/数字」和「字符串转不成整数」分开处理。

## 五、`finally` 的三条实测语义

### 5.1 `try` 里 `return`，`finally` 仍然执行

```python
def f():
    try:
        return "try"
    finally:
        print("finally 仍然执行")

print(f())
```

```text
finally 仍然执行
try
```

### 5.2 `finally` 里 `return` 会吞掉异常

```python
def g():
    try:
        raise ValueError("会被吞")
    finally:
        return "finally 的返回值"
```

```text
finally 的返回值
```

异常消失了，调用方永远不知道出过错。Python 3.14+ 甚至直接给 `SyntaxWarning: 'return' in a 'finally' block`。**`finally` 只做清理，不做返回。**

### 5.3 `finally` 不负责「恢复」

`finally` 不会把程序状态回滚，也不会自动重试。它只是「无论走哪条路都执行这一段」。文件关闭、连接释放、临时文件删除，才是它该干的事。

## 六、裸 `except:` 和 `except Exception` 的差别

实测（手动抛 `KeyboardInterrupt` 模拟 Ctrl+C）：

```text
裸 except: 接住了 KeyboardInterrupt
except Exception 没接住，KeyboardInterrupt 继续向上传播
```

`KeyboardInterrupt` 和 `SystemExit` 都直接继承 `BaseException`，不继承 `Exception`。裸 `except:` 等价于 `except BaseException:`，会把用户按 Ctrl+C、程序调用 `sys.exit()` 全部吃掉，表现为「程序退不出去」。

规则：

| 写法 | 接住什么 | 建议 |
| --- | --- | --- |
| `except:` | 所有 `BaseException` | 不要写 |
| `except Exception:` | 绝大多数业务异常，不含 Ctrl+C / `SystemExit` | 只在最外层兜底时用 |
| `except ValueError:` | 只接这一种（含子类） | 首选，越具体越好 |
| `except (ValueError, OSError):` | 接住列出的多种 | 相关的几种可以合并 |

## 七、`except` 的顺序：先具体，后笼统

```python
try:
    raise ValueError("原始错误")
except Exception:
    print("Exception 先接住")
except ValueError:
    print("这行不会出现")
```

实测输出：

```text
Exception 先接住，后面的 ValueError 分支永远到不了
```

Python 从上往下匹配，**第一个匹配的 `except` 获胜**。父类写在前面，子类分支就是死代码。`ValueError` 的继承链实测：

```text
ValueError -> Exception -> BaseException -> object
```

所以 `ValueError` 必须写在 `Exception` 前面。

---

## 八、正确的三段式：校验 → 执行 → 兜底

把 `jump` 改成「输入校验 + 明确异常 + 调用方决策」：

```python
def jump(self, height):
    try:
        h = int(height)
    except (ValueError, TypeError) as exc:
        raise ValueError(f"高度必须是整数，收到 {height!r}") from exc
    if h <= 0:
        raise ValueError(f"高度必须是正数，收到 {h}")
    print(f"{self.name}跳了{h}厘米高！")
    return h
```

三个要点：

1. `except ... as exc` + `raise ... from exc` 保留原始异常链，排错时能看到根因。
2. 校验失败用 `raise`，而不是 `print` 完继续往下走。**函数要么返回结果，要么抛异常，不要用打印代替失败。**
3. `finally` 只留给真正的清理动作。这个函数没有需要清理的资源，所以不需要 `finally`。

如果希望调用方不处理异常也能知道成败，可以返回 `(ok, message)`，但**不要同时抛异常又返回 False**，两种契约混用会让调用方无所适从。

## 九、正面教材：`load_data` 的三层防御

[07_file_test.py:6-18](../07_file_test.py#L6-L18)：

```python
def load_data():
    if not os.path.exists(FILE_NAME):
        return {}
    try:
        with open(FILE_NAME, "r", encoding="utf-8") as f:
            data = json.load(f)
    except (json.JSONDecodeError, OSError):
        print("通讯录文件损坏或无法读取，已按空通讯录启动。")
        return {}
    if not isinstance(data, dict):
        print("通讯录文件格式不正确，已按空通讯录启动。")
        return {}
    return data
```

三层各挡一类问题：

| 层 | 挡什么 | 不写会怎样 |
| --- | --- | --- |
| `os.path.exists` | 文件不存在 | `FileNotFoundError`（虽然也是 `OSError`，但提前判断语义更清楚） |
| `except (JSONDecodeError, OSError)` | 内容不是合法 JSON / 读不了 | 启动即崩 |
| `isinstance(data, dict)` | JSON 合法但类型不对（`[]`、`"abc"`、`123`） | 后面 `contacts[name] = phone` 会以奇怪方式失败 |

沙箱实测（把 `contacts_data.json` 换成不同内容后启动）：

```text
内容 '{broken'      -> 通讯录文件损坏或无法读取，已按空通讯录启动。
内容 '["a","b"]'    -> 通讯录文件格式不正确，已按空通讯录启动。
内容 '{"张三":"138"}' -> 正常进入菜单
```

这就是「异常处理 + 数据校验」的正确分工：`try` 负责「读得到吗」，`isinstance` 负责「读出来的东西能用吗」。

## 十、`assert` 不能当异常处理

```text
python -c "assert 1 == 2, '断言失败'"       -> AssertionError，exit=1
python -O -c "assert 1 == 2, '断言失败'"    -> 这行执行了，断言消失，exit=0
```

`python -O` 会把 `assert` 整句删掉。所以：

- 测试里的断言、调试期的自检：可以用 `assert`
- **参数校验、业务规则、安全边界：必须用 `raise`**

把「用户输入必须为正」写成 `assert h > 0`，在 `-O` 下等于没写。

## 十一、易错清单

| 写法 | 问题 | 改法 |
| --- | --- | --- |
| `except ZeroDivisionError` 但 `try` 里没有除法 | 死代码，误导读者 | 删掉或补上真正的除法 |
| 只捕获 `ValueError` | `None`、列表等输入抛 `TypeError`，直接崩 | 按实际类型捕获，或先做类型校验 |
| `print("错误")` 后继续执行 | 调用方以为成功了 | `raise`，或返回明确的失败结果 |
| `except Exception` 写在 `except ValueError` 前面 | 子类分支永远不执行 | 具体在前，笼统在后 |
| 裸 `except:` | 吃掉 Ctrl+C 和 `sys.exit` | 用具体异常；最外层才用 `except Exception` |
| `finally` 里 `return` | 吞异常，还触发 `SyntaxWarning` | `finally` 只做清理 |
| 用 `assert` 校验用户输入 | `-O` 下消失 | 用 `raise` |
| 异常信息只写「出错了」 | 排错时没有上下文 | 带上变量值：`收到 {height!r}` |
